# 원자료·적재·수집 검증의 분리

## 입력 원칙

- 원자료 폴더 전체는 설계·적재 근거다. 수집 로직과 수집 판정 테스트는 이 폴더를 직접 읽지 않는다.
- 수집 입력은 DB에 적재된 값과 설정 값이다. 테스트는 DB 픽스처·mock으로 검증한다.
- 원자료 경로를 테스트 설정에 넣지 않는다. 이번 변경은 기존 경로를 재지정하지 않았다.
- 원자료 검증은 수집 검증과 별도다. 검증하지 않은 원자료·계획을 수집 검증 통과로 대신 표시하지 않는다.

## 테스트 분류

- Python `source_test_policy.source_material_test`는 원자료 의존 메서드/클래스를 `unittest.skip`으로 표시한다. 실패하던 메서드 12개, 클래스 준비 2개와 원자료 계획 생성 2개를 대상으로 한다. 클래스 단위 제외는 해당 클래스의 모든 메서드에 적용된다.
- Java의 원자료 의존 메서드 2개에 JUnit `source-material` 태그를 붙였다. Maven 기본 검증은 이 태그를 제외한다.
- 태그·분류만 바꿨으며 기존 원자료 경로와 테스트 본문은 보존했다.
- `LocalCollectionControlTest`, `CollectionRunSchemaTest`, `tools/test_local_collection_control.py`는 mock/인메모리 DB·설정으로 검증한다. 원자료 제외가 실행 ID·스위치 검증을 대체하지 않는다.
- `t15ExactDisjointTargetsAndArrivalCountFormula` 전체가 원자료 의존이므로 이번 기본 수집 검증에서 제외된다. 따라서 이번 결과를 원자료 기반 T15 예산 검증까지 통과했다고 보고하지 않는다. 원자료 대조가 필요한 실제 노선/정류장 수 검증은 별도 적재 검증으로 남긴다.

## 별도 적재 절차

수집 기동이나 테스트 실행에 원자료 적재를 묶지 않는다. 기존 `local_collection_admin.py --apply`, `load_adopted_route_plan.py --apply`, `load_route_plan_windows.py` 등은 적재 도구이며 이번 작업에서 실행하지 않았다. 이 도구들에는 기존 원자료 참조가 남아 있다. 이번 작업은 경로를 고치거나 원자료를 복사하지 않으며, 기존 도구를 실행 가능하다고 승인한 것도 아니다.

후속 적재는 별도 승인·검증 단계에서 다음 순서로 수행한다.

1. 승인된 원본 파일을 확인한다. 다른 경로·같은 이름 파일로 자동 대체하지 않는다.
2. 대상 DB·테이블·적재 매핑을 검증한다. 수집 프로세스는 시작하지 않는다.
3. 트랜잭션으로 적재하고 실제 행 수와 제약을 확인한다.
4. 원본 파일명, 적재 시각(시간대 포함), 원본 행 수, 대상 테이블별 적재 후 행 수, 실제 변경 행 수, 성공/실패를 기록한다. 멱등 재실행이면 변경 0건을 그대로 기록한다.
5. 기록된 DB 스냅샷/설정 또는 동등한 mock으로 수집 검증을 실행한다.

기록 필드 예시(스키마 정의이며 실제 적재 기록이 아님):

```text
import_id, original_filename, imported_at, source_row_count,
target_table, target_row_count, changed_row_count, status
```

실제 적재를 하지 않았으므로 이번 작업에서 성공 레코드·행 수를 임의 생성하지 않았다. 기존 적재 이력에 이 필드들이 모두 있는지도 검증하지 않았다. 적재 도구의 감사 기록 구현·실제 적재는 별도 후속 작업이다.
