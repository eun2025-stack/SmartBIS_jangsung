- 기준일: 2026-10-02

## 1. 목적 및 운용 개념

SmartBIS는 내부망의 콘텐츠 제공 자료를 서버에 안전하게 인입하고, 서버가 콘텐츠·정류소 도착·재난 정보를 정책에 따라 선택하여 차량 내 Android 화면에 제공하는 시스템이다. 내부망에서 사전 승인된 자료가 전달되는 운영을 전제로 하므로 외부 제공자에 대한 별도 신청·승인 워크플로는 현재 요구범위에서 제외하고, 대시보드의 콘텐츠 기능은 기존 게시 자료의 조회와 게시 상태 관리에 집중한다.

## 2. 구현 상태 정의

| 상태 | 뜻 |
|---|---|
| 검증됨 | 해당 경로의 실행 결과가 사용자 시험 또는 기록된 직접 시험으로 확인됨. 운영 규모·장시간 안정성까지 뜻하지 않는다. |
| 부분 구현/검증 | 일부 코드와 흐름은 동작하지만 실제 데이터 공급원, 운영 경계 또는 종단 시험이 빠져 있음. |
| 미구현 | 현재 소스에서 해당 기능을 확인하지 못했거나 화면/API가 실제 데이터와 연결되지 않음. |
| 외부 승인/연동 대기 | 내부 구현과 별도로 제3자 서비스 이용 승인·정상 인증정보가 필요함. |
| 결정 필요 | 사업·운영 주체가 계약, 우선순위 또는 데이터 형식을 확정해야 구현을 완료할 수 있음. |

## 3. 사용자 및 시스템 경계

1. **콘텐츠 제공자**: 내부망에서 배치 폴더와 manifest, 선택적 미디어를 전달하고 완료 표시 `.ready`를 마지막에 생성한다.
2. **운영자**: 보호된 대시보드에서 게시 콘텐츠 상태와 표출 정책을 조회·관리하고, 오류 이력을 검색한다.
3. **서버**: Spring Boot API와 Node.js batch watcher, PostgreSQL, Nginx TLS로 구성한다.
4. **Android 클라이언트**: 차량 번호로 다음 표출 항목을 요청하고 텍스트·이미지·동영상을 화면에 표시한다.
5. **외부 데이터 서비스**: TAGO 및 행정안전부 재난문자 API. 현재 실서비스 수집기는 연결되지 않았으며 승인·인증과 구현이 남아 있다.

외부 네트워크 진입점은 Nginx HTTPS 8443 하나다. Spring Boot 8080과 PostgreSQL 5432는 Compose 내부 전용이다. 별도 외부 Tomcat과 `/sht_webapp/` 배포는 사용하지 않는다.

### 4.2 콘텐츠 인입 및 보존

| ID | 요구사항 | 현재 상태 |
|---|---|---|
| SR-INGEST-01 | 자료 전송이 끝난 배치만 `.ready`와 `contents.json`이 모두 있을 때 처리한다. | 검증됨: 폴링 watcher와 수동 배치 시험 |
| SR-INGEST-02 | JSON은 한 배치의 여러 콘텐츠를 포함하며 각 `content_id`가 DB 행을 식별한다. | v1/v2 계약 구현됨. v2 실제 배치에서 다섯 콘텐츠가 ID별 저장되고 첨부 메타데이터가 연결됨. 기존 v1 단일 파일 JSON도 호환 |
| SR-INGEST-03 | 파일 크기·수정시각 안정화 후 미디어 실재 여부를 검증한다. | 구현·시험 기록 있음. 기본 10초 간격×3회, 시험용 환경변수 override 가능 |
| SR-INGEST-04 | 검증·저장에 실패한 원본 자료를 버리지 않고 오류 위치와 운영 DB에 기록한다. | 구현 및 PostgreSQL 통합 검증됨: 잘못된 JSON이 error 경로와 batch `FAILED`/error `OPEN`으로 기록되고, 같은 배치 재처리 성공 시 `PROCESSED`/`RESOLVED` 확인. DB 장애 fallback은 미검증 |
| SR-INGEST-05 | 콘텐츠 파일은 날짜/배치 폴더로 보관하고 API에서 안전하게 제공한다. | 검증됨: 호스트 `server/content-store/YYYY-MM-DD/BATCH_ID`(컨테이너 `/app/content-store`), 새 자산은 root 기준 상대경로, 기존 절대경로는 호환. 순번별 API 다운로드 HTTP 200 확인 |
| SR-INGEST-06 | 인입 데이터·파일·DB 갱신을 재시도 가능하고 일관되게 처리한다. | 부분 구현: DB 일괄 트랜잭션 및 `content_id` UPSERT. 파일 복사와 SQL은 원자적이지 않아 orphan/중복 파일 정리 기준 미완료 |
| SR-INGEST-07 | 처리 오류는 운영 대시보드에서 기본 최근 3일, 상태/키워드 전체 검색으로 조회한다. | watcher→PostgreSQL lifecycle, 관리자 로그인, dashboard HTML 및 요약/목록 API HTTP 200 검증됨. 오류 행 0건은 시험 데이터 정리 상태와 일치. populated row의 화면 렌더링은 미확인 |

콘텐츠 입력 계약은 `schema_version=2.0`을 확정했으며 v1 호환 입력도 계속 받는다. 업무 category(`NOTICE`/`EVENT`)와 표현 형식(`POSTER_TEXT`/`TEXT`/`CARD_NEWS`/`IMAGE`/`VIDEO`)을 구분하고 자산마다 역할·순번·파일명·MIME·크기·SHA-256을 관리한다. `V010__content_data_contract_v2.sql` 적용 후 축제 포스터 5건·동영상 5건·카드뉴스 2건을 한 실제 배치로 저장했다. 기존 13개 콘텐츠를 교체하고 신규 12건 모두 활성 10초 스케줄을 등록했다. `SAMPLE-001` 표출 API에서 카드뉴스와 정렬된 네 장의 이미지가 반환됨을 확인했다. 자세한 계약 및 2026-10-04 교체 이력은 `SmartBIS_Content_Data_Contract_v2_Proposal_20261004.md`에 기록한다. 배치 처리는 상시 watcher의 Asia/Seoul 04:00 일정이 기본이며 `.ready` 없는 폴더는 처리하지 않는다. 개발 즉시 처리 모드는 운영 스케줄과 별도다.

### 4.3 정류소·노선·도착정보

| ID | 요구사항 | 현재 상태 |
|---|---|---|
| SR-BUS-01 | TAGO 정류소 API에서 정류소와 좌표를 가져와 장성읍·남면 등 행정 지역에 매핑한다. | TAGO 동기화와 `regions`/`bus_stops.region_id` DB 구조가 있다. 2026-10-03 관리자 전용 지역 목록/생성, 정류소 검색·페이지 조회, 지역 지정/해제 API와 수집 상태 대시보드 UI를 구현했다. | SR-BUS-02 | TAGO 노선 API에서 노선과 정류소 순서를 가져온다. | `cityCode=36450` 장성군 105개 노선 동기화 완료. 2026-10-03 최종 동기화 DB: 경유 행 5,339, 고유 정류소 951. 현재 `UP=2,062`, `DOWN=2,572`, `UNKNOWN=705`이며 미분류는 18개 노선 경로에 남아 방향 추론 로직 추가 검토 중. 원본 TAGO `updowncd=2` 의미를 공식 정의로 단정하지 않으며 현장 차량 위치 기반 도착 시험은 별도 |

| SR-BUS-04 | 차량이 정류소 100m 안에 있을 때 이번/다음 정류소 도착정보를 표출한다. | 거리·다음 정류소는 차량 GPS와 DB 경로로 계산. Android 상단 중앙 오버레이는 다음 정류소와 TAGO 노선·정류소 도착예정 API의 분 단위 ETA를 함께 표시한다. ETA API는 노선·정류소 기준이며 응답에 차량번호가 없으므로 특정 차량만의 ETA로 보장하지 않는다. 미제공/오류 시 분을 임의 계산하지 않고 정류소명만 표시 |
| SR-BUS-05 | 도착정보 표출 종료/유효기간 및 반복 정책을 운영 DB 설정에 따른다. | 일부 구현: `arrival_predictions` 만료와 `display_policies` 조회 코드. 정확한 현장 진입/이탈 조건은 실측 검증 필요 |

2026-10-02 `.env` 키로 정류소정보 도시코드와 승인된 버스노선정보를 실조회해 장성군 `cityCode=36450`, 노선목록 105개를 확인했다. 경유 정류소·노선 순번·좌표 동기화용 ADMIN API `POST /api/v1/admin/tago/catalog/sync`와 DB 현황 `GET /api/v1/admin/tago/catalog`을 구현하고 대시보드 수집 상태 화면에 실행/새로고침 버튼을 추가했다. 외부 응답 전체를 먼저 검증하고 성공한 뒤 트랜잭션으로 upsert한다. Maven 단위시험 3건과 backend 배포/health 확인은 완료했으나, 관리자 POST의 최종 성공 응답 및 실자료 DB 건수 확인은 아직 완료되지 않았다. `TAGO_ENABLED=false`는 자동 위치 polling에 유지한다. 지역명은 TAGO가 반환하지 않으므로 읍·면 매핑은 별도로 해야 하며, 위치조회 예시(`cityCode=25`, `routeId=DJB30300052`)는 장성군 실운행 자료가 아니다.

관리 대시보드는 A안 좌측 메뉴형으로 정했다. 메뉴 자체가 실제 연동을 보장하지 않는다. 외부망 신청/승인 workflow는 현 운영 합의상 요구범위가 아니고, ‘데이터 관리’는 게시 중인 콘텐츠를 관리하는 용도다.

### 4.6 표출 선택과 우선순위

합의된 기본 의도:

```text
관리자가 지정한 강제 표출(정책이 허용하는 경우)
  > 정류소 도착정보
  > 재난정보
  > 해당 정류소 지역 제한 콘텐츠
  > 지역 제한 없는 행사·공지/홍보 콘텐츠
```

지역 제한 콘텐츠는 유효한 100m 이내 도착 예측의 `next_node_id`에서 다음 정류소 지역을 얻어 `target_regions`와 비교한다. 지역을 찾지 못하면 지역 제한 콘텐츠는 선택하지 않고 지역 무관 콘텐츠만 후보로 둔다. `ArrivalService`는 새 예측에 current/next 정류소 ID를 저장한다. 합성 DB 통합시험에서 지역 도착정보 후 지역 콘텐츠 선택 및 지역 미상 차량의 전역 콘텐츠 fallback을 확인했다. 아직 실제 TAGO 자료로 지역명·정류소 매핑을 확인하지 않았으므로 실운행 검증 완료는 아니다.

| ID | 요구사항 | 현재 상태 |
|---|---|---|
| SR-DISP-01 | 다음 화면은 arrival → 정책상 시점의 disaster → 활성 scheduled content 순으로 선택한다. | 샘플 통합 검증: 동일 다음 정류소의 도착정보를 중복 반환하지 않고 다음 선택 단계로 진행. 새 정류소 예측은 다시 우선 표출 |
| SR-DISP-02 | 운영자는 타입별 우선순위와 표출/반복 간격을 바꿀 수 있다. | 정책의 `enabled` 및 `priority`가 표출 선택에 적용된다. 도착정보·재난·예약 콘텐츠 후보 중 활성 정책의 우선순위가 가장 높은 항목을 선택하고, 동순위는 도착정보→재난→일반 콘텐츠로 정한다. 예약의 `force_display`가 켜진 콘텐츠는 우선 후보로 취급한다. API의 `displaySeconds`는 Android 텍스트/이미지 타이머 및 동영상 종료 전환에 사용된다. 2026-10-03 Maven 25개 테스트 통과, backend 재배포 및 health `UP`. 정책값을 실제 운영자 화면에서 변경하고 연속 표출 순서를 확인하는 통합시험, 타입별 반복간격의 전체 의미는 추가 검증 대상이다. |
| SR-DISP-03 | 도착정보는 실제 100m 진입부터 정류소 기준 종료까지 유효하게 처리한다. | 현재 만료 prediction을 쓰는 기반 로직만 확인. 차량 GPS 실측 및 종료 운영 조건은 미검증 |
| SR-DISP-04 | 재난은 지정 반복 간격으로 재표출하고 사용자가 수동 조작하지 않아도 일반 콘텐츠와 순환한다. | 샘플 서버 API/Android 연속 흐름 부분 검증. 재난 반복의 장시간 무인 운행 검증 필요 |
| SR-DISP-05 | 강제 표출, 타입별 예약, 지역별 필터, 동일 콘텐츠 중복방지를 적용한다. | 지역 필터는 `target_regions`와 다음 정류소 지역을 비교하도록 구현 및 합성 DB 시험. 강제 표출/반복 정책의 완전한 계약·TAGO 기반 지역 정합성·현장 종단은 미완료 |

현재 `display_policies` 기본 migration 값은 개발 초기값이다. 운영 DB에서 시험을 위해 값을 바꾼 적이 있으므로 현재 실값은 DB를 조회해야 한다. `enabled`와 숫자형 `priority`는 ARRIVAL/DISASTER/일반 예약 콘텐츠 후보 간 선택에 반영되며, 동순위인 경우 도착정보→재난→일반 콘텐츠가 tie-break 기준이다. Android는 API가 반환한 `displaySeconds` 또는 동영상 종료에 따라 다음 항목으로 전환한다. 실제 운영자가 값을 조정해 연속 표출을 확인하는 현장 종단시험과 타입별 반복 간격 장시간 시험은 남아 있다. 표출 초는 콘텐츠 제공자가 임의 정하는 것이 아니라 지자체 운영 정책으로 관리한다.

## 5. DB 및 데이터 수명주기 요구

주요 테이블은 콘텐츠, 배치 오류, 운영 정책, 지역/정류소/노선, 차량 위치·도착 예측, 재난, 표출 스케줄 및 상태를 포함한다. 실제 테이블 목록은 DB에 존재하지만 TAGO ingest·지역 그룹핑이 자동 운영된다는 의미는 아니다.

Migration SQL은 `server/database/migrations/V001`~`V012`에 모여 있다. 기존 V010 콘텐츠 v2, V011 TAGO 동기화 이력에 이어 V012는 Android heartbeat 상태 테이블을 추가했다. V012는 2026-10-05 기존 DB에 적용하고 POST upsert를 확인했다. Flyway/Liquibase ledger가 없어 이전 이력은 별도 대조 대상이다. 이후 SQL은 실제 스키마를 확인해 수동 적용·기록하며 volume 초기화로 해결해서는 안 된다.

콘텐츠 게시 제외는 `content_publication_controls`의 상태 override로 처리하고 `contents`와 파일을 보존한다. 새로운 배치가 기존 `content_id`를 UPSERT하더라도 게시 override가 지워지지 않도록 분리되어 있다.

| `/api/v1/admin/display-policies` | 정책 조회/수정 | 권한 인증; 운영 효과 전체 종단 검증 필요 |
| `/api/v1/admin/ingest-errors...` | 운영 오류 검색 | DB 오류 조회와 watcher 쓰기 연계 구현; 관리자 브라우저 종단 확인 대기 |

## 7. 검증·수용 기준

개별 기능 검증은 다음을 모두 남긴다: 사용한 데이터가 실측/샘플 중 무엇인지, 실행 명령 또는 API, 예상 결과, 실제 결과, 오류 및 해결, 남은 제한. DB health UP은 버스·재난·배치 기능의 종단 작동을 대신하지 않는다. 빌드 성공은 컴파일 성공이지 외부 API 정상 응답이나 Android 현장 운영 성공을 뜻하지 않는다.

운영 수용 전 최소 종단 시나리오:

1. 다중 콘텐츠와 각 파일이 포함된 배치를 전달하고 `.ready` 생성 후 04:00 처리, DB 행, 파일 위치, 오류 기록을 대조.
2. invalid JSON·누락 파일·잘못된 지역·DB 일시 장애를 주입해 입력 보존, 오류 DB 기록, dashboard 조회, 재처리를 확인.
3. TAGO API 인증/정류장/노선/차량 위치를 실제 응답으로 수집하고, 차량 번호·운행 방향·다음 정류장·100m 경계 전후를 실측 비교.
4. 재난 외부 승인 후 실제 수신 메시지부터 만료/지역 필터/반복 정책과 Android 표시까지 확인.
5. 지자체 테스트 자료로 poster+text, text-only, multi-image card, image, disaster, video를 1920×1080 단말에서 각각 시험하고 영상 종료·정책 변경·연결 끊김 후 복구 확인.
6. 대시보드에서 콘텐츠 중지·복구, 표출 정책 변경, 실패 배치 오류 검색과 실제 단말 반영을 확인.
7. 백업에서 복구, 인증서 교체, 관리자 로그아웃·세션 만료 및 장시간 무인 운행 확인.

## 8. 단말 관리·MDM 등록 요구사항

| ID | 요구사항 | 현재 상태 |
|---|---|---|
| SR-MDM-01 | Headwind MDM 서버는 SmartBIS와 논리적으로 분리하고 HTTPS/MQTT 경로로 단말을 관리한다. | 별도 Compose 및 개발 HTTPS 진입점 부분 검증; 운영 이전/복구 시험 미완료 |
| SR-MDM-02 | 신규 BIT를 등록하고 Device Owner 상태를 확인한다. | 미완료. WTK-051D Android 11 시험 기기는 HMDM 미설치·Device Owner 미등록이며 Android provisioning은 완료 상태 |
| SR-MDM-03 | 등록 단말에 SmartBIS 앱을 원격 배포·업데이트하고 재부팅 후 자동 실행을 확인한다. | 미검증. Agent/서버 버전 호환성, MQTT, 실제 기기 설치가 남음 |
| SR-MDM-04 | 신규 등록·장애복구·백업복원 절차를 지자체 운영자가 재현할 수 있도록 문서화한다. | 절차서 작성 중. 제조사 프로비저닝 지원 및 실기기 시험 결과를 반영해 인수인계본 확정 |

`Device provisioned: true`는 Android 초기 설정 완료를 뜻하며 Device Owner 등록의 증거가 아니다. QR 등록은 장비 펌웨어의 Managed Provisioning 지원이 확인된 경우에만 적용한다. 공장 초기화 등 데이터 삭제가 가능한 작업은 승인된 시험 단말에 한정한다. 상세 절차와 실제 시험 경계는 [Headwind 기기 등록·운영 절차서](../deployment/headwind-mdm/DEVICE_PROVISIONING_RUNBOOK.md)를 참조한다.

## 9. 현재 판정 및 다음 우선순위

기반 서버/TLS, 미디어 전달, 지역 조건 샘플, v2 콘텐츠 계약의 서버→DB→API→Android 빌드 경로를 구현했다. 이를 완성된 운영 시스템 판정으로 확대하지 않는다. 남은 작업은 오류 행 브라우저 렌더링 및 migration ledger 정리, TAGO 차량 위치 실차 검증/운영, 재난문자 외부 승인 후 collector 연결, 대시보드 자산 미리보기·실제 운영자 흐름, 서로 다른 카드뉴스 이미지의 24인치 화면 확인, 장시간 무인 순환 및 백업/복구 시험이다. v2 실제 단말 종단 시각시험은 아직 미완료다.

실행 순서는 [전체 구축 진행현황](00_SmartBIS_구축_진행현황.md)에 유지한다. 상세 테스트 및 문제 해결은 [backend](SmartBIS_egov-backend_Build_Log_v1.0_updated.md), [Node watcher](SmartBIS_Node_Watcher_Build_Log_v1.0_updated.md), [Nginx/CA](SmartBIS_Nginx_Private_CA_Test_Log_v1.0_updated.md) 누적 로그에 기록한다.
