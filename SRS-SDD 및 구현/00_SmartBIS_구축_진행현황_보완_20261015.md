# SmartBIS 구축 진행현황 보완 — 2026-10-15

> 기존 진행현황 문서의 마지막 기록(2026-10-05 이후)을 보완한다. 아래 내용은 대화 기록과 현재 확인 가능한 소스 코드 기준이다. 실행 중 DB·단말 상태를 직접 확인하지 못한 사항은 완료로 간주하지 않는다.

## Headwind MDM 및 단말 등록

- Headwind MDM 커스텀 서버/에이전트, Device Owner 설정, 자동 단말 ID 등록 및 차량번호 배정 흐름을 구성·시험해 왔다.
- 차량번호 등록 앱과 SmartBIS Client는 Headwind Applications 및 `Common - Minimal` 구성으로 배포하는 절차를 사용한다.
- 단말 차량 배정 정보는 SmartBIS 백엔드 DB에 반영되어 TAGO 위치 조회 대상 차량과 연결되어야 한다.
- 앱 업로드/구성 동기화, Device Owner 프로비저닝, 인증서 신뢰, 단말 간 ID·차량 배정 충돌 문제가 시험 중 제기되었다. 대량 등록 표준 절차와 롤백 검증은 계속 필요하다.

## TAGO 차량 위치 및 도착정보

- 도착정보 처리 흐름과 파일별 역할을 `docs/arrival-information-flow.md`에 정리했다.
- 코드상 TAGO 연동 API는 차량 위치 조회 `getRouteAcctoBusLcList`와 정류소 도착예정 조회 `getSttnAcctoSpcifyRouteBusArvlPrearngeInfoList` 두 개다.
- 현재 소스 기준 위치 수집은 활성 차량 배정에 연결된 고유 노선을 하나씩 순환 조회한다. 카탈로그 전체 노선 수와 실시간 배정 노선 수는 별개의 값이다.
- `ArrivalService`는 차량의 최근 2분 이내 위치를 사용해 노선·방향·정류장 순번으로 다음 정류소를 계산하고 거리, 100m 접근 여부 및 ETA를 반환한다.
- 소스 검토에서 위치 요청 실패 백오프(일반 실패 2분, HTTP 429 15분)와 위치 신선도 2분 기준의 상호작용, ETA의 노선·정류소 단위 캐시 및 대상 수에 따른 TTL을 확인했다. 이는 코드 분석 결과일 뿐, 특정 차량의 실제 장애 원인으로 확정된 것은 아니다.
- 2026-10-15 사용자가 보고한 시험 증상은 7530 도착정보 미표출/갱신 이상이다. 실행 DB 연결이 되지 않아 최신 위치, 계산된 다음 정류소, 실제 API 응답을 대조하지 못했으므로 원인 확정과 운영 반영은 미완료다.

## Android 운영 화면 및 차량 배정

- 클라이언트 도착정보 요청·화면 갱신·정류소 도착 전체화면·UI 표시는 각각 Repository, DisplayController, ArrivalDisplayWindow, NaturalDisplayView에 나뉘어 있다.
- 차량 배정 앱의 배정 취소와 배정/미배정 상태 구분, 차량 DB 목록 연동, 업데이트 후 SmartBIS Client 복귀에 대한 개선 요청이 있었다. 최신 APK의 현장 설치 및 동작은 별도 확인이 필요하다.

## 다음 확인 및 완료 기준

1. 실행 중 백엔드 컨테이너 이미지가 작업공간의 소스와 동일한지 확인한다.
2. SmartBIS DB의 활성 단말 차량 배정 수 및 고유 배정 노선 수를 확인하고 대시보드의 실시간 수집 대상 수와 대조한다.
3. 7530의 최신 `bus_positions` 행 → 해당 노선/방향/순번의 다음 정류소 → `/v1/arrival` 응답 → 단말 표출을 같은 시각 기준으로 추적한다.
4. 원인을 확인한 뒤 위치 수집 실패 재시도 및 ETA 캐시 정책을 수정하고 테스트·배포 결과를 기록한다.
5. 실제 운영환경 이관, 단말 대량 프로비저닝, 롤백, 운영·관리·사용자 매뉴얼은 검증 전까지 완료로 표시하지 않는다.
